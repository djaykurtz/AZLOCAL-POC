========================================================================
  SETTLED DESIGN (do not re-litigate)
========================================================================
  - Goal: FUNCTIONAL proof of concept. Prove Azure Local can host AKS /
    Docker / Terraform. NOT production HA/DR/performance validation.
    Source: poc_kubernetes_test_plan.txt, the original task notes ("test if it works").
  - Scope: 4 active nodes (AZL-NODE-01..04) + 2 spare (05/06). ADR 0004.
  - Network: SINGLE CONVERGED INTENT on one subnet. mgmt + compute + S2D
    storage on the same NIC(s). No RDMA config, no jumbo, no DCB/PFC.
    Source: docs/prerequisites.md, the POC plan (topology: single-converged-intent),
    the original subnet request. This is a SUPPORTED topology, decided 2026-05-22.
  - Storage: Storage Spaces Direct from the validated NVMe data disks in
    each node. This is the cluster's storage; the network only carries the
    replication traffic between nodes. Both are needed; neither is wasted.
  - Connections per node: the written plan specified ONE converged link per
    node (6 IPs for 6 nodes). Dual-NIC / dual-connection storage was NEVER
    in the plan; it is a production-grade option deliberately traded away
    for POC simplicity. Optionally add a 2nd link later for resilience
    (config change, not a rebuild).

========================================================================
  - Azure Local supports dynamic scaling 1 -> 16 nodes. Add ONE node at a time.
  - Supported jumps: single-node -> two-node (two-way mirror, switch OR
    switchless, WITNESS REQUIRED); two -> three (three-way mirror, SWITCH ONLY,
    witness optional); three -> N (three-way, SWITCH ONLY).
    => 3+ nodes REQUIRES a switch. A switchless start caps at 2 nodes.
  - HARD gate on add: new node must have the SAME NUMBER of data drives, or
    the add is BLOCKED (error). CPU/mem lower only warns. -> keep drive counts
    identical across nodes (our storage-symmetry work already aligns).
  - Scaling out FROM single-node requires FIRST: (1) configure quorum witness,
    (2) configure storage intent (Set-StorageNetworkIntent) if not done at deploy.
  - New node needs: matching OS image (same solution version), Arc registration
    with SAME RG/Region/Sub/Tenant, and roles (HCI Device Mgmt, Key Vault
    Secrets User, etc.). Storage rebalance runs after add (can take days, low pri).
  - Cannot permanently remove a node once added.
  RECOMMENDATION: if nodes are ready, deploy the multi-node cluster directly
  (simpler than the add-node dance: no witness+intent+rebalance+possible
  switchless->switched transition). Use phased add-node only if blocked on
  getting all nodes ready at once. The NIC-Up gate (B1) is identical either way.
