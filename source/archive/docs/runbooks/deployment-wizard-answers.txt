CARD SWAP RUNBOOK (added 2026-07-24, donor updated to node 05) - unblocks SUBSYS mismatch
--------------------------------------------------------------------------
Problem: wizard Trigger deployment settings validation call failed with
  "DriverVersion, ComponentId, InterfaceDescription, RDMA not matched for edge
  device AZL-NODE-02 with AZL-NODE-01"

Root cause (proven on-node via Get-PnpDevice hardware IDs):
  01 Port3+Port4 : both PCI\VEN_15B3&DEV_1017&SUBSYS_008015B3
  02 Port3       : PCI\VEN_15B3&DEV_1017&SUBSYS_008015B3  (matches, keep)
  02 Port4 (#2)  : PCI\VEN_15B3&DEV_1017&SUBSYS_000615B3  <-- MISMATCH, replace
  04, 06         : both PCI\VEN_15B3&DEV_1017&SUBSYS_008015B3
  03 (spare)     : 2 cards SUBSYS_008015B3 - kept as untouched fallback donor
  05 (defr)      : 2 REAL cards SUBSYS_008015B3 (see PnP-ghost note below) - DONOR

Donor choice: node 05.
  Reasoning:
    - 05 is already disqualified from the cluster because it failed the NVMe
      check (wrong drive count/type). Removing a NIC from it changes nothing.
    - 03 remains our clean 2-card fallback if the 05 harvest ever damages the
      card in transit.

PnP-ghost note (do NOT be confused by the earlier enumeration on 05):
  The earlier scan showed 4 Mellanox entries on 05 (Adapter, #2, #3, #4).
  #3 and #4 are STALE PnP records - they share the SAME PCI bus/device/function
  as the two Up cards (bus 160/159, dev 0, fn 0). Two devices cannot occupy the
  same PCI address. #3 and #4 are leftover Windows device entries from cards
  that used to be in those slots. Node 05 has exactly TWO physical Mellanox
  cards, and both are SUBSYS_008015B3.

Exact card to remove from node 05 (the DONOR):
  Windows friendly name : Mellanox ConnectX-5 Adapter #2
  MAC                   : 00-00-5E-00-53-03
  Windows slot (Get-NetAdapterHardwareInfo.SlotNumber) : 5
  PCI bus               : 159
  Location string       : PCI bus 159, device 0, function 0
  Rationale             : same slot/bus number as the bad card on node 02.
                          Installing donor into the same physical slot on 02
                          gives Windows the best chance of enumerating it
                          back as 'Port4' with no manual rename.

Exact card to remove from node 02 (the BAD card being replaced):
  Windows friendly name : Mellanox ConnectX-5 Adapter #2
  MAC                   : 00-00-5E-00-53-02
  Windows slot (Get-NetAdapterHardwareInfo.SlotNumber) : 5
  PCI bus               : 159
  Location string       : PCI bus 159, device 0, function 0

At-rack procedure (smart-hands):
  1. Verify Dell service tags at rack:
       Node 02 service tag = (record from the chassis label)
       Node 05 service tag = (confirm at rack before opening the chassis)
  2. Power both nodes down gracefully (Stop-Computer or iDRAC graceful shutdown).
  3. Open node 05, remove the Mellanox card in the SAME physical slot that
     Windows reported as slot 5 / PCI bus 159 (the port whose MAC is
     printed on the sticker if visible - both ports of a card share that MAC
     as the base MAC).
  4. Open node 02, remove the bad Mellanox card in its slot 5 / PCI bus 159
     (MAC 00-00-5E-00-53-02). Keep it labeled and set aside; do NOT put it in
     node 05 (that would just move the problem). Node 05 keeps its one remaining
     Mellanox card - it is not going anywhere.
  5. Install the donor card from step 3 into node 02's now-empty slot.
  6. Cable up node 02's NEW card to the same 100G switch port that the old card
     used, so the storage-fabric wiring is identical to 01/04/06.
  7. Power node 02 back on. (Node 05 can stay off - it's benched.)
  8. Wait for Windows to enumerate (~2-5 min after boot).

Remote post-swap verification (from your workstation):
  a. Confirm both Mellanox cards on node 02 now report SUBSYS_008015B3:
       Invoke-Command azl-node-02.lab.example.com -Credential $c -ScriptBlock {
         Get-PnpDevice -Class Net | ? InstanceId -match 'VEN_15B3' |
           % { $hw=(Get-PnpDeviceProperty -InstanceId $_.InstanceId -KeyName DEVPKEY_Device_HardwareIds).Data;
               $sub=($hw|?{$_ -match 'SUBSYS_'}|Select -First 1) -replace '.*SUBSYS_([0-9A-F]+).*','$1';
               '{0}  SUBSYS={1}  status={2}' -f $_.FriendlyName,$sub,$_.Status } }
     Expected: both SUBSYS=008015B3, both status=OK.
  b. Check NIC naming with Get-NetAdapter. If the newly-enumerated card came
     up as 'Ethernet 7' (or similar) instead of Port4, rename it:
       Rename-NetAdapter -Name '<new name>' -NewName 'Port4'
     Also re-verify the 'Management' NIC name is still 'Management' and the
     other storage NIC is still 'Port3'.
  c. Refresh Azure edgeDevices inventory on node 02 so the wizard re-reads
     the new hardware (the cached one is what it validated against):
       az resource delete --ids /subscriptions/00000000-0000-0000-0000-000000000001/
         resourceGroups/rg-azlocal-poc-001/providers/Microsoft.HybridCompute/
         machines/AZL-NODE-02/providers/Microsoft.AzureStackHCI/edgeDevices/default
         --api-version 2024-04-01
     Alternative: restart the DeviceManagementService on the node and wait a
     few minutes for the resource to repopulate.
  d. Re-open the deployment wizard and click Start validation. It should now
     get past the cluster consistency preflight and into the on-node
     Environment Checker (~15 min for 4 machines).

All wizard input values above remain unchanged - no re-entry needed.
